Hanterill reads Diagnostic Trouble Codes with the UDS ReadDTCInformation service from every ECU that answers a diagnostic session.

## Status, not just a code

Each DTC carries a status byte. Hanterill presents it as one of:

| State | Meaning |
| --- | --- |
| Active | The fault is present now. |
| Pending | Seen once, not yet confirmed over enough drive cycles. |
| Stored | Confirmed and recorded. |
| Historical | Previously set, since cleared, retained as a record. |

A single "check engine" light can sit on top of one active code and several historical ones. The
status is what tells you which is which. The fault list opens filtered to what needs attention:
active and unconfirmed codes first, the quiet history one keystroke away.

## Freeze frames and snapshots

Where the ECU stored a snapshot at the time of the fault, Hanterill retrieves it with the code: the conditions recorded when the DTC matured. Not every code has one.

## Scanning

Hanterill uses four ReadDTCInformation subfunctions: report the number of DTCs by status mask, report the DTCs by status mask, report a snapshot record for a DTC, and report an extended data record for a DTC.

A report-by-status-mask exchange, with the bytes on the wire:

<DiagnosticExample
  service="ReadDTCInformation, report DTCs by status mask"
  request="19 02 FF"
  response="59 02 FF <dtc><status> <dtc><status> ..."
  note="The FF mask asks for every status. Each three-byte DTC is followed by one status byte; Hanterill classifies that byte as active, pending, stored or historical."
/>

Hanterill runs this per ECU and aggregates the result into one list, grouped by module.

## Clearing

Clearing diagnostic information (UDS `0x14`) changes ECU state. It is compiled out of released
builds and exists only in builds made with the explicit `unsafe-write-ops` feature; a standard
binary refuses with a typed response and the capability manifest reports it as unavailable. See
[Safety](/docs/safety).

Where it is compiled in, the clear follows the orchestration modelled on the reverse-engineered
reference: enter the extended session per module, capture the freeze frames that the erase would
destroy, run a bulk clear, wait through the pending-response window, retry per-ECU, then verify
with a re-read and report the modules still holding codes (the stubborn set). An optional,
opt-in force-reset loop reboots those modules, re-activates the DoIP route after the reboot and
clears once more; it is suppressed while the vehicle reports a driving usage mode. Per-module
selective clearing ("clear this module") uses the same tracked operation with one target, and the
whole run is recorded as evidence in the session archive.

## Diffing scans

Two scans of the same car compare inside the app: codes added, codes cleared, status transitions,
and the pre-erase snapshots kept above. The DTC diff is one of four built-in comparisons; the
others cover cell history, firmware inventory and the full [inspection report](/docs/inspection-reports).

## Evidence workflow

Scan, do the repair, scan again. Both sessions are already archived locally; open the diff and the
result is two columns instead of a claim. Exports to JSON and CSV carry the same records with the
VIN redacted by default.

Modern cars report their own problems. Each one is filed as a DTC: a Diagnostic Trouble Code, a
short code like `P0A80` that points at a specific fault in a specific system. Hanterill reads them
from every module that will talk.

## A code is not the whole story

Every DTC comes with a status byte: extra bits that say more about the fault than the code itself.
Hanterill turns those bits into plain states:

| State | Meaning |
| --- | --- |
| Active | The fault is happening right now. |
| Pending | It happened once, but has not been confirmed over enough drive cycles yet. |
| Stored | Confirmed and recorded by the module. |
| Historical | It was set, then cleared, but the module still keeps the record. |

One warning light can sit on top of a single active code and five old historical ones. The status
is what separates them. Hanterill opens the fault list filtered to what needs attention first,
with the quiet history one keystroke away.

## Freeze frames

When a module sets a fault, it often saves a snapshot of the car at that exact moment: speed, pack
temperature, voltage, what the driver was asking for. That snapshot is called a freeze frame, and
it is usually far more useful than the code alone.

Hanterill reads it with the code where one exists. Not every fault has one.

## What a scan actually sends

Hanterill uses four ReadDTCInformation subfunctions: count the codes by status mask, list the
codes by status mask, read a snapshot record, and read an extended data record.

The main exchange, with the bytes on the wire:

<DiagnosticExample
  service="ReadDTCInformation, report DTCs by status mask"
  request="19 02 FF"
  response="59 02 FF <dtc><status> <dtc><status> ..."
  note="The FF mask asks for every status. Each three-byte code is followed by one status byte; Hanterill decodes that byte into active, pending, stored or historical."
/>

The scan runs per module and aggregates into one list, grouped by module. A module that does not
answer is listed as not observed, never as healthy. A clean scan result tells you how many modules
replied, not only that nothing was found.

## Before and after: the diff

The most useful thing you can do with fault codes is compare two scans. Scan before the repair,
scan after, and open the DTC diff. Codes added, codes cleared, status changes, and the pre-erase
snapshots all sit side by side.

Both sessions are already saved locally, so the comparison is a local calculation. No car needed.

## Clearing codes

Clearing is a write, and Hanterill treats it like one. It sits behind an explicit confirmation and
the runtime capability check, and a build compiled without the write feature refuses it with a
typed response instead of an unexplained failure.

When the operation runs, it follows an orchestrated sequence modelled on the reference tool:

1. Open an extended session with each module.
2. Capture the freeze frames first, because the erase destroys them.
3. Send the bulk clear.
4. Wait through the module's "busy" window.
5. Retry per module where needed.
6. Re-read to verify, and report the modules still holding codes (the stubborn set).

An optional force-reset step reboots those stubborn modules, repairs the link and clears once
more. It is opt-in, and it is suppressed while the car reports a driving mode.

Per-module clearing ("clear this module") uses the same machinery with one target. The whole run
is recorded as evidence in the session archive.

<Callout kind="caution" title="Clearing is not fixing">
Erasing a code removes the record, not the fault. If the underlying problem is still there, the
code comes back. Use the diff to prove a repair, not to make a light go away.
</Callout>

## Exports

Scans export to JSON and CSV. The CSV exporter neutralises spreadsheet formula injection (a cell
starting with `=`, `+`, `-` or `@` cannot execute in Excel), and the VIN is redacted by default.

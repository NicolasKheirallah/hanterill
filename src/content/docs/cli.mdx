Hanterill ships a command-line companion, `hanterill`. It reaches the same engine
the desktop app uses: every command goes through the same use cases, and every structured document
it emits is versioned.

Use it to script a scan, diff two sessions over a weekend, or read a car
without opening a window.

<Callout kind="note" title="Some commands never touch a car">
`show`, `did-analyze`, `did-kb`, `did-plan`, `did-presets`, `firmware-diff`, `cells-diff`,
`dtc-diff`, `export`, `replay`, `vendor-ref`, `vendor-dids` and `service-families` work entirely
offline. Everything else needs exactly one transport source.
</Callout>

## Invocation

```text
hanterill <command> [args] <transport> [--json | --format <fmt>]
```

The transport flags tell the CLI where a car is:

| Flag | Meaning |
| --- | --- |
| `--discover` | Find a car on the local network and connect to it |
| `--ip <addr>` | Connect to a car at a known address |
| `--replay <corpus>` | Replay a recorded request/response file instead of a car |
| `--mock <scenario>` | A built-in simulated car, for tests and development builds |

## Output and exit codes

With no format flag you get readable text. `--json` emits a versioned document (the first field is
always `schema_version`), and `--format text|json|csv` selects explicitly. Missing values are JSON
`null`, never placeholder text. Files are written atomically, so a partial document is never left
on disk.

| Exit code | Meaning |
| --- | --- |
| 0 | The command completed and coverage was complete |
| 1 | Bad invocation, a transport failure, or a clean result with incomplete coverage |

That second case is deliberate. A scan that could not reach every module exits 1, because "no
codes found" and "no codes found in the four modules I could reach" are different answers.

## Offline intelligence

The DID tooling never contacts a car, which makes it the part you can run on a plane:

| Command | What it does |
| --- | --- |
| `show <ecu> <dtc bytes...>` | Decode a fault code from bytes you type |
| `did-scan` | Sweep an identifier range on a car, or against `--capture` for a saved CSV |
| `did-scan-all` | All-module bounded sweep: presence, catalogue, optional discovery, with a request budget |
| `did-watch` | Re-read a small set of identifiers on an interval |
| `did-analyze` | Mine saved captures for unknown positives and contract mismatches |
| `did-kb` | Query or fold the learned identifier knowledge base |
| `did-plan` | Preview a bounded scan plan without contacting anything |
| `did-presets` | List the discovery-range presets |
| `firmware-diff` | Compare two firmware inventories, module by module |
| `cells-diff` | Compare two cell-voltage captures, group by group |
| `dtc-diff` | Compare two DTC scans |
| `retrofit-check` | Compare a car's build list against a supplied option-to-module expectation file |
| `export` | Unpack a saved session into modular JSON or CSV files |
| `replay` | Replay a recorded live-telemetry run through the virtual-time engine |
| `vendor-ref`, `vendor-dids`, `service-families` | Sanitized vendor reference vocabulary: what exists, never a decoded value |

## Structured output

Everything versioned starts with `schema_version`. Two examples worth knowing:

- `scan --json` emits a `dtc-scan/2` document with per-module evidence: the SHA-256 of each raw
  response, its length, wire timing, NRC codes, skip reasons, and the retry set. A negative
  response keeps its NRC instead of being reported as a malformed positive reply.
- `did-scan-all --json` emits a `did-scan-all/2` artifact with per-row NRC, hashes and latency,
  plus a promotion-evidence block for uncatalogued positives. `--tier raw|support|public` controls
  how much is redacted.

## Read versus write

The read commands above stay inside the read-only service set. A separate group changes the car:
`clear-dtcs`, `reset`, `epb`, `bms-reset`, `service-reset`, `usage-mode`, the calibration helpers
(`climate-calibrate`, `sunroof-init`, `steering-zero`, `grille-calibrate`, `camera-learn`,
`blindspot-reset`, `adas-reset`), `aux-pump`, `security` and `tcam-battery-test`.

Those require explicit confirmation, are governed by [Safety](/docs/safety), and a build compiled
without the write feature refuses them with a typed message.

## Scripting a repair

The JSON documents are stable and versioned, so diffing two sessions is a shell pipeline:

```text
hanterill scan --discover --json > before.json
hanterill scan --discover --retry-of before.json --json > after.json
hanterill dtc-diff before.json after.json
```

`--retry-of` re-reads only the modules the first pass left failed or unread, then merges the result
back with lineage showing both passes. The original file is never modified.

For battery work: capture `battery-cells --json` before and after, then run `cells-diff` to see
per-cell deltas. A cell that was not read on one side keeps a gap rather than a zero.

Every read Hanterill makes is kept as evidence, not as a screenshot or a PDF: what was asked, what
came back, when, and by which decoder it was interpreted. This page explains what a session is, how
comparisons work, and what each export format is for.

## What a session contains

The archive is one JSON document, schema v4. It holds sessions, raw blobs, observations, fault codes,
artifacts, DID applicability and diagnostic responses. A session record itself is smaller than that
sounds: an id, the vehicle reference (the owner's full VIN), a contract version, a created time and a
note. There is no end time and no app version on the record.

What the desktop actually saves is one JSON artifact per subsystem:

- the diagnostic report
- battery cells and battery thermal
- the ECU inventory
- the firmware audit
- the parasitic drain
- optionally, a live recording, a DID scan, a DID scan-all and a DTC clear

Each artifact carries an id, a kind, a schema version, a JSON body and a SHA-256. A capture manifest
sits alongside them with the start and stop times, the captured and failed counts, and the derived
semantics. The report artifact is the richest. It carries the app version, the policy id and version,
the score, the verdict, the findings, the coverage gaps and a checksum.

Raw evidence is designed in, but not written today. The raw-blob, observation, DTC and
diagnostic-response tables exist, with verbatim exchanges and hashes, yet no production code path
currently writes them, and loading a session never returns raw evidence. "The raw bytes stay alongside
the decoded number" is a designed capability, not current behaviour.

<Callout kind="note" title="Where sessions live">
The archive is `sessions.json` under your OS data directory, with an in-memory fallback. Deleting a
session removes its artifacts and its evidence. Retention defaults to 90 days, with 30, 90, 365 or
keep-forever as the options; it is enforced at startup and when the setting changes. There is no total
archive size cap. See [Privacy](/docs/privacy) for retention and deletion.
</Callout>

## Comparing two sessions

Five diff domains are built in, and each one answers a different question:

| Domain | The question it answers |
| --- | --- |
| DTC faults | What changed between the scan before the repair and the scan after? |
| Battery and cells | Has any cell group drifted since the last visit? |
| ECU network map | Did a module appear, or stop answering? |
| Firmware SBOM | Did the software on any module actually change? |
| Vehicle genome | Did the car's build configuration (`0xC010`) change? |

There is no "full report comparison". The DTC domain reports four triage buckets: Newly Tripped,
Resolved, Persistent and Unverified.

Each domain aligns the two sessions by a stable identifier rather than by position:

| Domain | Aligned by |
| --- | --- |
| Cells | physical index |
| Firmware and ECU maps | module address |
| DTCs | module plus code only: status is displayed, but it is not part of identity |
| Car configuration | option index, that is, position |

Missing coverage is preserved, and never counted as a fix. A fault present in the baseline but absent
in the target is Unverified, not Resolved, when the target did not cover that module. A cell that was
not measured keeps a null delta. Cross-vehicle and cross-contract comparisons are refused outright.

Battery readings come back improved, degraded, unchanged or not measured. Firmware comes back
matching, updated, behind or missing. Car configuration comes back matching, retrofitted, deactivated
or changed.

Separately from the diff domains, the battery page keeps a baseline-versus-current drift ledger for
SoH, spread, weakest cell and discharge ceiling. Its noise bands are 0.5 % SoH and 2 mV spread, so a
variation inside those bands reads as normal rather than as movement.

The CLI exposes the DTC, cell and firmware diffs as commands of their own; the other domains live in
the app.

## Exporting

The session dialog offers five choices, and ZIP is only packaging, never a content format:

| Choice | What it produces |
| --- | --- |
| CSV ZIP (default) | the modular CSV set, packaged as one archive |
| JSON ZIP | the modular JSON set, packaged as one archive |
| Separate CSVs | the same CSVs, written as individual files |
| Separate JSONs | the same JSONs, written as individual files |
| Single JSON | one consolidated document for the whole session |

The modular set covers the manifest, battery, cells, thermals, DTCs, ECUs, firmware, live telemetry,
parasitic drain, service schedule, vehicle summary and diagnostic report. The report builder
additionally offers PDF, HTML, JSON, CSV and Markdown, and its contents are selectable:
DTC freeze frames, the cell voltage map and the ECU software BOM can each be included or left out.

The CLI is narrower: `export` writes JSON or CSV directories only. It produces no ZIP, no single-file
document and no PDF.

<Callout kind="caution" title="Spreadsheet safety">
A CSV cell starting with `=`, `+`, `-` or `@` can execute as a formula when the file is opened. Both
the app's exporters and the CLI neutralise those prefixes before writing, so a fault description can
never become a live formula in Excel.
</Callout>

## VIN masking at export time

Every session export dialog shows the VIN-masking choice, and masking is on by default. The interface
export keeps the first six characters and the last four, with asterisks between them. The app's
reports, the CLI and the support bundle use a three-letter-prefix style such as `ABC...1234` instead.

One path does not honour the choice: the single-JSON export ignores the masking checkbox and writes
the full vehicle reference. Treat that file as unmasked, whatever the dialog said.

The support bundle is stricter regardless of the setting: it scrubs serial numbers, GPS coordinates,
IP addresses, email addresses and credentials before a file leaves the machine.

## Importing

Import accepts one camelCase document and rejects unknown fields. It requires an exact contract
version of `1.0`, between 1 and 100 artifacts, and a 64-hex SHA-256 on each artifact that matches its
content. Report artifacts must also pass a report checksum. The UI caps the file at 5 MB and the
backend at 10 MiB. A new id is derived from the masked vehicle only.

Honest caveat: none of the app's own exports match this import schema, so an export-then-import
round-trip is not guaranteed. Import does not re-score what it loads.

## Re-scoring an old session

The inspection report carries the version of the rule set that produced its score, so a stored session
can be re-scored under the current policy (v1.0.0) without reconnecting to the car. Re-scoring verifies
the report, re-evaluates it and returns both the previous and the current verdict, findings and
coverage gaps. It is read-only: the stored artifact is never rewritten, and the report's SHA-256
checksum still tells you whether a file has been altered since it was written.

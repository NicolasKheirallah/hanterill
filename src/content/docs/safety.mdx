A diagnostic tool can do two very different things: ask the car questions, or tell the car to do
something. Hanterill keeps those worlds apart. This page explains exactly where the line sits and
how the app enforces it.

## Reading is the default

Every read path in Hanterill transmits only services that ask questions:

| Service | What it asks |
| --- | --- |
| `0x10` | Open a diagnostic session so the module will answer |
| `0x19` | Read fault codes |
| `0x22` | Read a value by identifier |
| `0x24` | Read how a value is scaled |
| `0x3E` | "Still here", so the car does not fall asleep mid-scan |

There are two narrow carve-outs beyond that list, and both only read:

- `0x31 0x03` reports the stored result of a routine that already ran. It never starts or stops
  anything.
- The `0x2A` periodic read can register one on-demand sample and cancel it again. The unsolicited
  repeating modes are refused.

Nothing in that set changes the car, and it is the same set in every build.

## Writing exists, and it asks first

The released build ships the state-changing commands. A workshop tool that cannot clear a code
after a repair is only half a tool. What keeps that safe is the confirmation step, not the absence
of the commands:

- Every write is a separate, explicitly confirmed action in the interface.
- The running binary publishes a capability manifest, and the interface only offers what the
  binary can actually do.
- A build compiled without the write feature refuses those commands with a typed `read_only_build`
  response. That stripped configuration exists for CI and development; it is not what ships.
- Hanterill never flashes modules, never unlocks security access (`0x27`) to write by identifier,
  and never performs programming services.

<SafetyNotice level="adaptation" title="What the write surface covers">
This surface covers clearing fault codes (`0x14`), starting service routines (`0x31`), ECU reset (`0x11`) and
gated memory reads (`0x23`). ECU reset is used only by the opt-in force-reset step in the clear
flow, and memory reads have a 256-byte cap and a caller-verified address list. The routine
identifiers are reverse-engineered. Even on a write-capable build, steering-angle and ADAS targets
must not be actuated without the manufacturer's procedure: Hanterill exposes the capability, not a
licence to use it.
</SafetyNotice>

## The clear flow, step by step

Clearing fault codes is the write most people will actually use. This is what happens after you
confirm:

1. Enter an extended session with each module. Manufacturer modules reject a clear in the default
   session, so this step is required.
2. Capture the freeze frames before erasing. The erase destroys them.
3. Send the bulk clear.
4. Wait through the module's pending-response window.
5. Retry per module where the bulk pass did not land.
6. Re-read the codes and report the stubborn set: modules still holding codes after the erase.

An optional force-reset loop reboots those stubborn modules, waits roughly five seconds, repairs
the route and clears once more. It is opt-in, and it refuses to run while the car reports a driving
usage mode.

## Traffic discipline

A diagnostic tool can flood a car just by being eager. Hanterill keeps its request volume bounded:

- Scans run bounded loops with request budgets, so a sweep cannot flood the gateway.
- Cancellation is cooperative: Hanterill checks between requests, so you can stop immediately
  instead of waiting for the whole sweep to finish.
- Sessions are meant for a parked car. Keep the car in Park with the parking brake on.
- Recovery never resets a module just because a request timed out.

## High voltage

<SafetyNotice level="high-voltage" title="High voltage is dangerous">
Electric cars carry several hundred volts of direct current. Reading battery data over a cable does
not de-energise anything and does not make physical high-voltage work safe. Servicing the pack, the
inverters or the orange cabling requires the manufacturer's procedures, equipment and training.
</SafetyNotice>

## Not a replacement for the manufacturer's tooling

Hanterill is independent and is not affiliated with Volvo Cars, Polestar or Geely. Do not make a
safety-critical repair decision on Hanterill output alone. This matters most on a platform still
marked Testing or Research, where decoding has not been checked against a real car.

## If something looks wrong

Stop. Do not run a routine to "fix" a reading you do not understand. Export the session, compare it
against a second scan or a known-good car, and ask in the project's discussions before acting. The
[support bundle](/docs/privacy) export is scrubbed for sharing.

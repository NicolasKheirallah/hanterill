Before Hanterill reads anything, it has to know which car is on the other end of the link. This page
explains how the app finds and reads the VIN, how it decides the platform, what a resolved vehicle
profile contains, and the guard that stops two cars from being treated as one.

## How the VIN is found

The VIN rule is one function: 17 alphanumeric characters after trimming, per ISO 3779. A payload that
fails the rule is not a VIN, whatever answered. The search walks a trust order and stops at the first
valid answer:

<SpecList rows={[
  ["1", "the VIN a vehicle announcement carried during discovery, which costs no wire traffic"],
  ["2", "the routed entity's address: one targeted read of 0xF190"],
  ["3", "one functional read of 0xF190, where several modules answer the same identifier"],
  ["4", "a sweep of the modules that report an active diagnostic session, each asked for its VIN"],
]} />

Silence at one step moves to the next; it is not a failure of the search. Cancellation is the only
error the search returns.

## How the VIN is read

The VIN comes from DID `0xF190` (ReadDataByIdentifier) through the same DID path every other read
uses. A response that is not 17 UTF-8 bytes is a typed failure, not an empty value. A module that does
not support the identifier stays unsupported, and one that stays silent is recorded as silent rather
than as a car with no VIN.

The identity read also pulls the CEM `0xEDA0` block, which carries diagnostic, hardware and serial
numbers. The two reads are independent, so a failure in one does not hide the answer from the other.

## Where the identity is shown

The Vehicle page puts the model and platform at the top, the VIN below it, and the source and capture
time underneath. The VIN is masked by default and can be revealed from the same toolbar. The observed
VIN is also published to a shared store, so another page does not have to read it again.

## How the platform is decided

Architecture detection scores evidence collected on a fingerprint. The classes and their weights are
fixed:

<SpecList rows={[
  ["15", "vehicle identity (VIN and model hints) and topology"],
  ["45", "exact controller identity, a diagnostic signature, or a DoIP entity signature"],
]} />

Repeated evidence inside one class earns no extra score. Two rules then apply: the winner needs at
least 60 points across at least two independent classes, and a margin of 25 points over the runner-up.
Below that, the verdict reads as a candidate or ambiguous, and when nothing qualifies the platform
reads unknown. Only live evidence can select a platform; cached and synthetic observations never raise
confidence.

## What a vehicle profile resolves

The resolved vehicle record carries everything a later use case needs: the architecture and its
confidence, the model, the model year, the catalogue profile, the pack topology with its own
confidence, the powertrain variant, and the reason slugs behind every fallback and default.

Two limits matter. The catalogue profile exists only when platform, model and model year are all
established; missing any one leaves the profile empty and names the gap. The model year comes from
configuration or factory evidence and is never inferred from the VIN or a build week. The model
identity itself is derived once, in the same place the detector scores with, so every page names the
same model.

Topology confidence is separate from the architecture verdict. It reads pinned when the populated
cell count lands on a topology whose platform agrees, inferred when the count is distinctive but the
platform is not confirmed, and defaulted when there is no usable count evidence or the count alone is
ambiguous. A 108-cell read cannot separate two platforms by itself, so it never pins silently.

## The identity guard

The guard has two halves. At connect, the app captures the CEM VIN once and arms the guard only on a
well-formed VIN. On a stage transition, it reads the live VIN again and compares:

<SpecList rows={[
  ["Same", "the live VIN equals the known VIN; the run continues"],
  ["Silent", "nothing answered or the payload was malformed; silence is not proof of a swap, so the run continues"],
  ["Mismatch", "a different vehicle answered; the run stops and carries the observed VIN as evidence"],
]} />

The policy lives in one module so every flow inherits it. The all-module DID scan rechecks on the
stage transition, and the fault-code sweep's reconnect-and-resume refuses to merge rows read from a
different vehicle. Un-attempted rows stay un-attempted after a mismatch.

<Callout kind="note" title="A demo session runs unguarded">
With no well-formed VIN to capture, the guard stays unarmed rather than arming on a guess. That is a
deliberate choice, and it means an unverified session carries no identity proof.
</Callout>

The same rule covers the `0xF114` factory build sheet. It is decoded against the connect-time VIN, and
if the record's VIN disagrees, the sheet becomes a typed not-applicable failure instead of a fact about
this car. An unknown connect-time VIN is silence, never a mismatch.

## Refusing cross-vehicle comparisons

Before two sessions are compared, the app compares the vehicle reference each one recorded. When both
carry a reference and the references differ, the check returns a mismatched-vehicle result with the
comparison refused: deltas taken across two cars mislead. When either side has no recorded identity,
the result is an unverified-vehicle warning rather than a block, and the app asks you to confirm both
sessions belong to the same car. Contract versions must match as well. The diff framework and its
alignment rules are described in [sessions and evidence](/docs/sessions-and-evidence).

## How ECU addresses are resolved

Callers name a role or a registry short name plus the resolved vehicle and get the address for that
platform. CMA resolves from the live-verified registry; SPA and SEA1 resolve only from their own DoIP
registries, and a name with no mapping on that platform returns nothing. An unresolved architecture
uses the CMA first-contact fallback, and that answer is flagged as assumed. SPA2 returns nothing. A
role that fans out across several controllers, such as the drivetrain, returns nothing because no
single address is correct; the caller records the read as not attempted instead of guessing.

## What the app cannot say

- The VIN search can return nothing. A demo or unverified session then runs without the guard.
- Model identity depends on the VIN grammar or a live identity. A car the grammar does not know stays
  unidentified, and the page shows the platform without a model.
- No model year means no catalogue profile, however confident the platform verdict is.
- SPA2 addresses are not mapped, so role lookups there return nothing.
